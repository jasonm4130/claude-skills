# Codifying Subagent-Driven Development as a Deterministic Workflow

A design brief for replacing the disabled superpowers post-plan suite
(`subagent-driven-development`, `executing-plans`, `dispatching-parallel-agents`,
`test-driven-development`, `using-git-worktrees`, `finishing-a-development-branch`,
`requesting-code-review`, `receiving-code-review`, `verification-before-completion`)
with one workflow-driven skill — the SDD loop as code, not as a flowchart the
controller walks by hand.

---

## Executive summary

Codifying the SDD loop as a deterministic Workflow script is not just sound — it is
the textbook-recommended pattern. The implement → review → fix → repeat → final-review
loop has **known, predictable structure**, which is precisely the condition under which
Anthropic recommends a *workflow* (control flow in code) over an autonomous *agent*.
Microsoft's Conductor (May 2026) productionizes exactly this for "review loops,
plan-then-implement"; a 2026 source-code audit found 8 of 13 coding agents hardcode the
outer loop and let the model drive only the decisions inside it; and Claude Code's lead
Boris Cherny calls the practice "writing loops." Today's prose-SDD is the *model-driven*
version of a loop that should be code.

The crucial nuance — and a correction to one over-stated source claim — is that
codifying the loop does **not** hardcode the *judgment*. The scaffold drives the loop;
the model still decides what to build, whether a review passes, and how to fix. That is
the orchestrator-worker split our `deep-dive/fanout.mjs` already embodies.

Six concrete deltas the research adds versus a naïve port of the SDD skill, plus one
scope caution, are in [Design implications](#design-implications-for-the-skill).

---

## 1. Determinism vs. model-driven orchestration (core; reliability: medium)

**Workflows beat autonomous agents for known-structure tasks — by recommendation and in
production.** Anthropic's canonical taxonomy splits agentic systems into *workflows*
(LLMs orchestrated through predefined code paths — predictable, consistent, lower cost)
and *agents* (the LLM dynamically directs its own control flow — flexible, higher cost,
compounding-error risk). The stated rule: use the simplest thing that works, and add
autonomous agency only when "it's difficult or impossible to predict the required number
of steps." A plan-driven dev loop is the opposite of unpredictable.
([Anthropic, Building Effective Agents](https://www.anthropic.com/research/building-effective-agents), 2024-12-19, *partial* — the workflow/agent definitions are verbatim, but the worker mischaracterised the archetype list as "four" when the source has five and slightly over-stated how much of orchestrator-workers is hardcoded; the subtask *selection* is model-driven.)

- **Microsoft Conductor (2026-05-14, *supported*):** workflows declared in YAML, routing
  via Jinja2 expressions, "the orchestration layer consumes zero tokens." The team's
  explicit lesson: "The workflows we keep reaching for — review loops, research
  pipelines, plan-then-implement — have known structure. We'd rather have predictability,
  cost control, and auditability than replanning flexibility." Human gates, parallel
  groups, and loop-backs live in the graph, not in a planning LLM.
  ([Conductor blog](https://opensource.microsoft.com/blog/2026/05/14/conductor-deterministic-orchestration-for-multi-agent-ai-workflows))
- **Source-code audit of 13 coding agents (arXiv 2604.03515, 2026-04-10, *partial*):**
  8 of 13 implement the outer loop as an imperative `while True` in scaffold code — the
  loop is hardcoded, the LLM selects actions inside it; only loop *termination* is
  model-driven. Agentless sits at the fully-deterministic extreme (no feedback loop),
  Moatless Tools at the autonomous extreme (full MCTS). *(The "three-phase Agentless"
  detail was mis-imported from a different paper; the core counts — 8/13, 7/13 ReAct,
  11/13 compose multiple primitives — are confirmed. Single primary source for the
  numbers.)*
- **Production preference** (Gartner <5% of enterprise apps have real agents as of late
  2025) is driven by predictability, fixed cost, and auditability. *(The "95% choose
  workflows" framing is a logical leap — "not having agents" ≠ "chose workflows" —
  downweight that gloss; the Gartner baseline itself is real and multiply corroborated.)*

**Takeaway:** the SDD loop belongs in code. The model fills the nodes (implement, judge,
fix); the workflow guarantees the nodes happen in order and none get skipped.

## 2. Codifying YAGNI / anti-over-engineering (core; reliability: medium)

**Agents over-build by training incentive, and YAGNI survives free generation.** LLM
coding agents optimise for "comprehensive-looking" output drawn from mature production
codebases where abstraction is appropriate; throwaway-simple code is under-represented in
training data. *(Reported impact — 76% more LoC, 39% cognitive-complexity rise — is
single-source and unverified; treat as directional, not measured.
[agentpatterns.ai](https://agentpatterns.ai/anti-patterns/abstraction-bloat/), *partial*.)*

- **Kent Beck (2026-06-25, *supported*):** YAGNI was never about saving typing. It carries
  two price-theory bills that survive free generation — the **optionality** bill
  (premature structure commits on a guess and spends the option to build the right thing
  once you know) and the **NPV** bill (cost pulled forward, value pushed back). Free
  generation makes violations *cheaper to commit and therefore worse*: "the genie will
  happily build you a beautiful speculative framework, and you'll pay both bills just the
  same — plus you'll comprehend it less, because you didn't write it."
  ([essay](https://newsletter.kentbeck.com/p/the-cost-yagni-was-never-about))
- **The fix is a three-part stack:** (1) an explicit simplicity directive in the agent's
  instruction ("write the minimum that satisfies the spec; no features, abstractions, or
  error handling beyond what is specified"), (2) a design/approval gate before coding,
  and (3) a **spec-compliance reviewer that hard-gates on "nothing more, nothing less"**
  before code-quality review is even reached. The research independently surfaced
  **obra/superpowers' own task-reviewer** as the canonical implementation of (3) — its
  "Extra" verdict catches over-engineering, and a stated rationale ("left it per YAGNI")
  never downgrades a finding's severity.
  ([obra/superpowers task-reviewer](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/task-reviewer-prompt.md), *supported*)
- **Two-concrete-use rule** for abstractions: don't add an abstraction, mode flag,
  provider interface, or strategy object unless there are two concrete uses *in this
  change*. *(Real rule, but mis-attributed to the YAGNI page — it lives on the companion
  Speculative Generality page; [aipatternbook](https://aipatternbook.com/yagni),
  *partial*.)*

**The hard counter-boundary (consistent across every source, non-negotiable):** enforced
minimalism must **never** strip security, input validation, error handling, accessibility,
or observability. These are expensive to retrofit and exist for non-functional reasons.
The distinction is **"we know we need this → build it"** vs. **"we might need it someday
→ don't build it yet."** For financial / security / user-data code, the agent's tendency
to add validation "is a feature, not a bug."

**Takeaway:** ponytail's discipline maps directly onto SDD's existing spec gate. Codify
the *ladder* into the implementer and the *over-engineering lens* into the reviewer — both
fenced by the counter-boundary so they sharpen minimalism without starving robustness.

## 3. SOTA for the post-plan "execute" phase (background; reliability: medium)

Mid-2026 agentic execution has formalised around a five-stage loop — **discover → plan →
execute → verify → iterate** — until a verifiable stop condition holds. "Loop engineering"
(designing self-verifying harnesses) is described as the successor to prompt engineering;
Boris Cherny: "I don't prompt Claude anymore… My job is to write loops." *(quote
well-corroborated, *supported*.)*

- **Maker ≠ checker at the loop level:** Claude Code's `/goal` (v2.1.139, 2026-05-11) runs
  a separate, faster model (Haiku) after each turn to evaluate a completion condition from
  the transcript — it does not run tools. The agent that built the work and the agent that
  judges "done" are different instances. *(supported via official docs.)*
- **Verification signal hierarchy** (descending reliability): deterministic oracles
  (CI, unit tests, type checks, linters) > perceptual/visual signals > critic sub-agents
  (no worker context) > LLM self-critique (weakest — "rationalises its own mistakes").
  Production loops stack signal types; self-critique alone is not a valid done-signal.
  ([mer.vin](https://mer.vin/2026/06/loop-engineering-design-coding-agent-systems-instead-of-prompting-every-turn/), *partial* on a 5th tier, *supported* on the core four.)
- **Model tiering** is standard cost discipline: frontier orchestrator, mid worker, fast
  verifier — ~40% cheaper than all-Opus, codified in committed config so nobody defaults
  every agent to the most expensive model. ([CloudZero](https://www.cloudzero.com/blog/claude-code-agents), *supported*.)
- **Git worktrees** are the isolation primitive for parallel agents (4–8 per developer
  before human review becomes the bottleneck). *(specific ceiling soft / single-source.)*
- **Spec-driven development** (GitHub Spec Kit et al.) treats the spec as an executable
  contract with a Coordinator/Implementor/Verifier execution shape. **But** Fowler's
  Thoughtworks analysis (*supported*, strongest source) raises *Verschlimmbesserung*:
  elaborate multi-file markdown spec ceremonies create review overload without guaranteeing
  agent compliance; SDD's sweet spot is **bounded greenfield tasks with good test
  coverage**, not large ambiguous brownfield.
  ([Fowler](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html))

**Takeaway:** take the execution *shape* (coordinator/implementer/verifier, task
decomposition, deterministic test oracle, model tiering, worktree isolation) — not the
heavy spec apparatus. Our plan is already written by `writing-plans`.

## 4. Failure modes determinism introduces, and where to break the loop (follow-up; reliability: medium)

Hardcoding the loop introduces structural failure modes that the design must pre-empt:

- **Oscillation** (*supported*): the same defect class rejected twice means stop, don't
  retry forever — "stop is a valid terminal state." Halt after two same-class review
  failures and hand to a human, rather than spinning the fix loop.
  ([Shevchenko](https://gregshevchenko.com/notes/ai-agent-failure-loop-breakers/))
- **HITL cannot block in place** (*supported*): a background loop that pauses on a human
  collapses against real timeouts (API Gateway 29s, serverless 10–300s, OAuth token
  expiry). The fix is async — checkpoint, exit cleanly, resume on event. For us: the
  Workflow runs to completion and **never blocks on a human**.
  ([Digital Applied](https://www.digitalapplied.com/blog/human-in-the-loop-escalation-design-ai-agents-2026))
- **HITL bypass is the most-exploited failure mode** (Microsoft AI Red Team v2.0,
  2026-06-04, *supported*): gates left inside the loop get automated past. Hoist them
  before destructive operations; tier approvals by reversibility; summarise approval
  prompts from the underlying tool calls, not the agent's self-description.
  ([Microsoft](https://www.microsoft.com/en-us/security/blog/2026/06/04/updating-taxonomy-failure-modes-agentic-ai-systems-year-red-teaming-taught-us))
- **Deterministic escalation by model tier** (*supported via Exa*): a deterministic worker
  gets exactly **one** attempt ("retrying a deterministic model is provably useless"); a
  frontier model gets **up to two** error-steered attempts; then **halt**. A deterministic
  test harness gates promotion between tiers, and the top tier rarely solves what the
  second failed on. ([The CTO Advisor](https://thectoadvisor.com/blog/2026/05/17/who-determines-done-why-agentic-ai-needs-escalation-not-more-loops/))
- **Checkpoint after every step** (*partial*): durable state so recovery time stays
  constant. For us this is the Workflow `resumeFromRunId` journal plus a progress ledger.
  *(The "constant vs. unbounded recovery time" argument was not supported by the cited
  Google ADK page — downweight that specific framing; the checkpoint-per-tool-call
  mechanism is confirmed.)*
- **Thread AI's production SDLC harness** (*supported*): treat the non-deterministic model
  call with deterministic-workflow runtime semantics — durable queue, typed contracts,
  explicit retry policy, structured auditable events; rising human-override rates feed back
  as rule updates shipped to every future run.

*(Caution: a 385-fault agentic-AI study was cited with **specific fault patterns that do
not appear in the paper** — its real taxonomy is dependency-management / input-
interpretation / robustness / LLM-integration. Treat that finding's enumerated list as
unsupported; the high-level "agentic systems fail at the intersection of deterministic
bugs and LLM non-determinism" is confirmed.)*

## Design implications for the skill

Six deltas versus a naïve port of the prose SDD skill, plus one scope caution:

1. **Deterministic escalation ladder for BLOCKED** — cheap/deterministic worker: 1
   attempt → capable model with error fed back: up to 2 attempts → halt and return for
   the human. Replaces SDD's prose "re-dispatch with a more capable model."
2. **Oscillation breaker** — halt after two same-class review failures instead of looping
   the fix forever.
3. **HITL fully hoisted out of the loop** — pre-flight conflict scan before dispatch;
   plan-mandated / conflicting findings batched and returned for adjudication; the
   irreversible merge/PR step (`finishing-a-development-branch`) stays human-gated in the
   main session, never automated by the workflow.
4. **Test/CI as the authoritative done-oracle** — reviewer verifies against the diff,
   never trusts the implementer's report; self-critique is never the sole done-signal.
   (SDD already does maker≠checker; the research confirms the hierarchy.)
5. **Model set explicitly on every `agent()`** — ~40% cheaper than all-Opus, and satisfies
   the repo's own `workflow-model-guard` hook.
6. **Ponytail, codified and bounded** — implementer gets the ladder + simplicity directive
   + `ponytail: <ceiling>, <upgrade>` shortcut markers + one runnable check; reviewer gains
   the over-engineering lens (`delete / stdlib / native / yagni / shrink`, `net −N lines`),
   fenced by the hard counter-boundary (never cut security, validation, error handling,
   accessibility, observability). Optional post-loop ponytail-debt harvest of any
   `ponytail:` markers introduced during the run.

**Scope caution (ponytail on our own design):** per Fowler's *Verschlimmbesserung*
finding, build a **lean loop over an already-written plan** with test coverage — not a
spec-kit-style multi-file ceremony. Keep the skill thin; put the determinism in the
workflow, not in prose.
